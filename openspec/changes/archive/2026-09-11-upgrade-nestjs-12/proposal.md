# Proposal: Upgrade NestJS 11 → 12

## Goals

- **Eliminate the NestJS-family share of the `npm audit` vulnerabilities.** Baseline (verified 11 Sep 2026): **32 vulnerabilities (4 critical, 21 high, 5 moderate, 2 low)**. The NestJS block: `@nestjs/platform-express` 11.1.21 → `multer` 2.1.1 (plus the related no-fix `express`/`qs`/`body-parser` advisories) and `@nestjs/swagger` 11.4.4 → `js-yaml` 3.14.2. `@nestjs/platform-express` 12.0.1 ships `multer` 2.2.0 and `@nestjs/swagger` 12.0.1 ships `js-yaml` 5.4.1 — clearing the ~8 advisories (3 high + moderates) in the `multer`/`js-yaml` chains referenced by ROADMAP I01/D1. The patch fixes `@nestjs/platform-express@11.2.3` / `@nestjs/swagger@11.4.7` mentioned in the roadmap are **superseded** — the major already includes them.
- **Stay on a supported, current NestJS major before the P1 provider modules are built on top** — same rationale as the NX 23 upgrade: avoid stacking new code (OWID client, category modules) on top of a pending framework migration.
- **Keep every validation gate green with zero errors and zero warnings** — `npm run lint`, `npx nx build api`, `npx nx test api` (54 tests: 50 baseline + 1 direct rate-limit coverage from task 3.10 + 3 fallback coverage from task 2.2) plus `shared` (8) and `web` (221), coverage thresholds intact, a direct rate-limit test proving the 429 path of the held-back `@nestjs/throttler` 6.5.0 (task 3.10, user-approved option B), `npx nx serve api` bootstrap with a healthy `/api/v1/health`, a manual Swagger UI check, and the `npm audit` reduction verified and recorded.

## Non-Goals

- **No migration of project code to ESM** — `apps/api` stays CommonJS (explicit decision; NestJS 12 makes ESM adoption optional). The ESM-published `@nestjs/*` 12 packages are consumed through Node's native `require(esm)` (requires Node ≥ 20.19 / ≥ 22.12 — the repo runs Node 24.15).
- **No replacement of Joi with Standard Schema / Zod** — `@nestjs/config` 12 validates via Standard Schema but keeps the Joi path working (Joi ≥ 18 provides Standard Schema support; the repo has 18.2.8). The `class-validator` / `class-transformer` DTO workflow also stays exactly as-is.
- **No `@nestjs/throttler` upgrade** — stays at 6.5.0. No throttler release declares Nest 12 peer support yet (peers reach `^11` only, as of 11 Sep 2026). This is a deliberate, documented exception — see design.md.
- **No removal or weakening of the rate-limiting guard** — the global `ThrottlerGuard` (60 req / 60 s per IP) keeps working unchanged.
- **No Next.js, React, TypeScript, NX, Jest, or SWC upgrades** — only the `@nestjs/*` family changes (plus the `swagger-ui-express` removal). Root `package.json` is not touched. (Correcting the **stale README.md version cells** for Next.js, React, Playwright, ESLint, and Prettier **is** in scope as documentation-only fixes — user-approved scope addition; the packages themselves are not upgraded.)
- **No new features or product behavior changes** — every endpoint (`/health`, `/demo-validation`, `/water-footprint/products`) behaves identically before and after; this is regression-proofing, not functional change.
- **No fixing of remaining non-NestJS vulnerabilities** — the `semantic-release` subtree and `concurrently` → `shell-quote` families (release-tooling batch, renumbered to D2 after this change) and the no-fix-available advisories (`express`/`qs`/`body-parser`, `@xhmikosr/decompress`, `picomatch`, `fast-uri`, `ip-address`, `piscina`, `brace-expansion`, `postcss-selector-parser`) stay out of scope.
- **No `nest upgrade` CLI usage** — the repo does not use the Nest CLI (it builds via NX + `webpack-cli`); the migration is manual and controlled by design.
- **No CI workflow changes** — `.github/workflows/ci.yml` already runs Node 24 and `npm ci`; it requires no edits.
- **No commits, pushes, or PRs** — per explicit user decision, the implementation stays in the working tree; the user validates manually (Swagger UI, unit tests, E2E) before authorizing any commit. This proposal intentionally contains no commit/push tasks.

No `project.json` files are involved — the api's targets live in its `package.json` `nx` block and the `nx.json` inference plugins, none of which change.
