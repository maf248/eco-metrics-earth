# Design: Upgrade NestJS 11 → 12

## Overview

Toolchain maintenance change: move `apps/api` from NestJS 11.1.21 to the NestJS 12 line (latest stable as of 11 Sep 2026, exact pins) via a **manual, controlled migration** — no `nest` CLI (this repo builds with NX + `webpack-cli`), no codemods. The source footprint is one config-options nesting in `app.module.ts` plus one new test file (direct rate-limit coverage — user-approved option B, see "Held-back dependency"); everything else is dependency manifests, lockfile, and documentation. Validation is regression-focused: prove that everything that worked on Nest 11 works identically on Nest 12.

**State management / data flow:** unchanged. No application state, no data flow, no endpoint contract changes. The only runtime-observable differences expected are cosmetic (default logger output format).

## NestJS 12 breaking changes — what affects this workspace

### Affects us — must handle

1. **All `@nestjs/*` packages publish as ESM.** CJS consumers keep working via Node's native `require(esm)` (requires Node ≥ 20.19 / ≥ 22.12). The repo runs Node 24.15 (`.nvmrc` = 24) — satisfied. Jest ≥ 30.4 on Node ≥ 24.9 supports `require()` of ESM from CJS test files — the repo has Jest 30.4.2 + Node 24.15 — satisfied. The api tests run through `@swc/jest` 0.2.39 with a CJS `.spec.swcrc`. Although Jest 30.4.2 on Node ≥ 24.9 supports `require()` of ESM from CJS test files, the SWC transform still needs to be told which ESM packages to compile. `apps/api/jest.config.cjs` was updated with `transformIgnorePatterns: ['node_modules/(?!(@nestjs)/)']` — the minimal empirically-verified pattern — so `@swc/jest` transforms the ESM-published `@nestjs/*` 12 packages. Without this pattern the 54 api tests fail with "Cannot use import statement outside a module" — verified empirically with `--skip-nx-cache`. The webpack build (`NxAppWebpackPlugin`, `target: node`, `compiler: tsc`, `generatePackageJson: true`) externalizes `node_modules`, so the bundle emits `require('@nestjs/core')` etc. and Node 24 resolves the ESM at runtime — no `webpack.config.js` change expected.
2. **`@nestjs/config` 12 validates via Standard Schema.** Joi keeps working when ≥ 18 (repo: 18.2.8 ✅), but Joi-specific options must move under `validationOptions.libraryOptions`. In `apps/api/src/app/app.module.ts` (lines 26–29), `allowUnknown: true, abortEarly: true` move from `validationOptions` to `validationOptions.libraryOptions`. This is the **only source change** of the upgrade; the observable semantics (tolerate unknown vars, abort on first invalid var, schema defaults) are identical.
3. **Lifecycle hooks are invoked per component-hierarchy level.** Low risk here: the module tree is flat and simple (`AppModule` → `HealthModule`, `WaterFootprintModule`), and `main.ts` does **not** call `enableShutdownHooks()` (verified — no shutdown hooks are registered today, and Nest 12 does not require adding them). The full-app bootstrap test (`__tests__/app/bootstrap.test.ts`) starts the real application via `NestFactory.create` and is the empirical check for init-order regressions.
4. **`ConsoleLogger` structured params on by default.** The repo uses no custom logger; `main.ts` relies on the default logger and the bootstrap test passes `{ logger: false }`. Impact is limited to dev/prod server log output format (cosmetic). The E2E suite asserts HTTP response contracts, not log output (verified — `apps/web/e2e/` makes HTTP assertions only), so no assertion changes are expected. Flagged for the manual E2E run regardless.
5. **HTTP adapter error mapping rework — unmapped routes no longer reach NestJS exception filters.** Baseline Nest 11: `GET /api/v1/nonexistent` produced a `NotFoundException` that the global `AllExceptionsFilter` serialized as JSON (`{ success: false, error: "Cannot GET /api/v1/nonexistent", status: 404 }`). Nest 12 leaves these 404s to Express 5, which returns HTML. Fix: add a catch-all `FallbackController` (`@All('{*path}')`) in `apps/api/src/common/fallback/`, imported **last** in `AppModule`, which throws `NotFoundException` with the original `Cannot METHOD path` message and lets the existing global filter format the response. This restores byte-equivalent baseline behaviour for unknown routes without shadowing real endpoints. Verified empirically: `/api/v1/health`, `/api/v1/water-footprint/products`, and `/api/v1/demo-validation` keep returning 200; only unmapped paths return the JSON 404 shape.

## Dependency decisions

### Held-back dependency: `@nestjs/throttler` stays at 6.5.0 (user decision — do not reopen)

No `@nestjs/throttler` release declares Nest 12 in its peer range (peers reach `^11` only, as of 11 Sep 2026). Decision: keep 6.5.0 and validate empirically rather than block the upgrade on an ecosystem release.

- **Install:** `.npmrc` has `legacy-peer-deps=true` (I07), so npm will not reject the stale `^11` peer against `@nestjs/core` 12.
- **Runtime surface:** small and fully mapped — `ThrottlerModule.forRoot([{ ttl: 60_000, limit: 60 }])` + `ThrottlerGuard` as `APP_GUARD`, both in `app.module.ts` and nowhere else (verified by grep). No `@Throttle()` / `@SkipThrottle()` decorators are used anywhere. throttler 6.5.0 is CJS, so the Nest 12 ESM publishing does not change how the app loads it.
- **Empirical validation — corrected coverage picture:** the working assumption was "existing ThrottlerGuard unit tests + E2E rate-limit coverage". Inspection shows that is **not literally true**: no unit test exercises the guard directly (`app.module.test.ts` only compiles the module graph — which does include the guard provider and would catch DI resolution failures), and no E2E spec asserts 429/rate-limit behavior. The coverage is **indirect but real**: all 10 E2E API specs in `api-health.spec.ts` and the bootstrap test's health request pass through the global guard — a guard that fails to instantiate or throws on request would surface as 500s across those specs. **Direct rate-limit coverage added (user-approved option B):** a dedicated test exercising the 429 directly is now part of this change (task 3.10) — an E2E hammering spec or a unit test with a small-limit `ThrottlerModule`, coder's choice per the shared-budget analysis below. The requirement is a direct 429 assertion, not only inference from pass-through traffic.
- **Shared-budget analysis for the direct test (verified 11 Sep 2026):** the guard is global (`APP_GUARD`), but buckets are keyed per route handler + tracker IP (`sha256(<ControllerClass>-<handler>-<throttlerName>-<req.ip>)`) — only same-endpoint requests share a budget, and router-level 404s never reach the guard (they consume nothing). However, the Playwright suite runs `api-health.spec.ts` in **all 5 projects** (chromium-desktop runs every spec; firefox/webkit/mobile grep `@smoke`, and the API specs are `@smoke`-tagged) → `/health` already receives ~10 hits per full run from the same localhost IP, and the demo handlers ~15 each. Once a bucket is tripped it stays blocked for 60 s (`blockDuration` defaults to `ttl`) — any spec hitting that endpoint within the window receives 429 and fails. Consequence: an E2E hammering spec can contaminate the other API specs unless isolated (no `@smoke` tag, hammer-until-first-429, own project / serial mode); the unit form (`Test.createTestingModule` + small limit + supertest) avoids the shared budget entirely. Whichever form ships, **the full E2E suite must be verified to still pass end-to-end** — that is the acceptance criterion for this risk.
- **Verified 429 response shape (from the `@nestjs/throttler` 6.5.0 dist source — re-confirm empirically at implementation):** status 429; body `{ "statusCode": 429, "message": "ThrottlerException: Too Many Requests" }` (string-payload `HttpException` serialized by the built-in `BaseExceptionFilter` — no `Service Unavailable` payload in 6.5.0); `Retry-After` header in seconds; `X-RateLimit-Limit`/`-Remaining`/`-Reset` headers on normal responses.
- **If it fails:** document the failure mode in the change outcome and evaluate fallbacks — (a) hold the Nest 12 upgrade until a throttler release declares Nest 12 peers, (b) adopt a throttler pre-release if one ships Nest 12 support, or (c) gate the guard behind a feature flag while awaiting support. Rate limiting must not be silently removed.
- **Documentation:** the deliberate pin is recorded in AGENTS.md (Dependency Management) so future agents do not "fix" it unintentionally.

### Dead dependency removal: `swagger-ui-express`

Verified: `swagger-ui-express` appears only in `apps/api/package.json` (line 98) and in the generated `apps/api/dist/package.json` (build artifact). Zero imports in `apps/api/src` (grep). `@nestjs/swagger` has served its own `swagger-ui-dist` UI since v11 — the Swagger UI at `/api/v1/api/docs` already works without this package. Removing it drops its subtree from the lockfile. The stale `dist/package.json` that still lists it is regenerated by the next build (`generatePackageJson: true` plus the `prune-lockfile` / `copy-workspace-modules` targets).

Atomicity note: if the user later requests commits, this removal can be split into its own commit — that is a commit-time concern only; this change works in the working tree with no commits (user decision).

### Express / helmet / bootstrap

Express 5.2.1 is already installed today (via platform-express 11.1.21); `helmet` 8.3.0 already runs against Express 5. `main.ts` needs no changes: no `enableShutdownHooks()` exists and none is required by Nest 12; no custom logger to migrate.

## Alternatives considered

| Alternative                                                                             | Rejected because                                                                                                                                                    |
| --------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Patch-only security fixes (`@nestjs/platform-express@11.2.3`, `@nestjs/swagger@11.4.7`) | Superseded — the 12.x major includes them; would leave the repo on an older major with P1 modules about to be built on top (the exact situation D1 exists to avoid) |
| Wait for `@nestjs/throttler` Nest 12 peer support before upgrading                      | User decision: do not block the framework upgrade on an ecosystem release; validate 6.5.0 empirically instead                                                       |
| Migrate the api to ESM alongside the upgrade                                            | Explicit non-goal — Nest 12 makes ESM optional; CJS via `require(esm)` is supported on Node 24 and keeps the change minimal                                         |
| Migrate Joi → Zod / Standard Schema validation                                          | `@nestjs/config` 12 keeps the Joi path (Joi ≥ 18); the `class-validator`/`class-transformer` workflow also stays — migrating adds risk with zero functional gain    |
| Use `nest upgrade` / migration schematics                                               | The repo has no Nest CLI — NX + `webpack-cli` build; a manual pin-bump is smaller and fully reviewable                                                              |

## Migration strategy

Manual, working-tree only (no commits — user decision). Ordered steps:

```bash
# 0. Baseline
npm audit --json > audit-baseline-nestjs12.json   # record: 32 (4 critical, 21 high, 5 moderate, 2 low)

# 1. Upgrade the @nestjs/* pins in the apps/api workspace scope (exact versions)
npm install --save-exact @nestjs/common@12.0.1 @nestjs/core@12.0.1 \
  @nestjs/platform-express@12.0.1 @nestjs/swagger@12.0.1 @nestjs/config@12.0.0 \
  --workspace=api
npm install --save-exact --save-dev @nestjs/testing@12.0.1 --workspace=api
#    (equivalent deterministic path: hand-edit the seven pins in apps/api/package.json,
#     then run a single root `npm install` — guarantees exact pins with no caret risk)

# 2. Remove the dead dependency
npm uninstall swagger-ui-express --workspace=api

# 3. The one source change: app.module.ts — validationOptions → validationOptions.libraryOptions

# 4. npx nx reset   # clear stale daemon/cache state after the dependency swap

# 5. Validate (gates below)
```

## Security outcome — audit baseline and expectation

### Baseline (verified 11 Sep 2026)

`npm audit`: **32 vulnerabilities — 4 critical, 21 high, 5 moderate, 2 low.** NestJS-family vulnerable packages: `@nestjs/platform-express` (via `multer` 2.1.1; the related `body-parser` and `qs` advisories have no fix available), `@nestjs/swagger` (via `js-yaml` 3.14.2).

### What the NestJS 12 upgrade eliminates

- `@nestjs/platform-express` 12.0.1 ships `multer` 2.2.0 — expected to clear the `multer` advisory chain. **Outcome at implementation:** 2.2.0 still carries 3 high advisories (verified via a clean isolated install), so the pre-planned root `overrides` fallback was triggered — a top-level `"multer": "2.3.0"` pin in the root `package.json` (equivalent to the nested form and the one that resolved cleanly after a full lockfile regeneration). Final audit: 21 advisories, zero `multer`/`js-yaml` mentions.
- `@nestjs/swagger` 12.0.1 ships `js-yaml` 5.4.1 — clears the `js-yaml` chain.
- The ROADMAP's patch fixes (`11.2.3` / `11.4.7`) are superseded by the major.

### Expected remaining (out of scope, with owners after renumbering)

| Family                                                                                                                                                                    | Advisories          | Fix path                      | Owner                |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------- | ----------------------------- | -------------------- |
| `semantic-release` subtree (`npm`, `@npmcli/*`, `libnpm*`, `pacote`, `sigstore`, `@sigstore/*`, `tar`)                                                                    | ~14 incl. criticals | semantic-release 25 batch     | D2 (release tooling) |
| `concurrently` → `shell-quote`                                                                                                                                            | 2 critical          | patch 9.2.4 / concurrently 10 | D2                   |
| No-fix-available (`express`, `qs`, `body-parser`, `@xhmikosr/decompress`, `picomatch`, `fast-uri`, `ip-address`, `piscina`, `brace-expansion`, `postcss-selector-parser`) | various             | upstream fixes                | tracked in I01       |

**Expectation:** the total drops by ~8 (32 → ~24). The acceptance criterion is "zero advisories whose vulnerable chain routes through `multer` under `@nestjs/platform-express` or `js-yaml` under `@nestjs/swagger`" — not a specific total. The `express`/`qs`/`body-parser` advisories are expected to remain (no fix available); their presence after the upgrade is **not** a failure of this change.

## Validation gates (all must pass, zero errors and zero warnings)

1. `npx nx reset` — clean cache/daemon state after the dependency swap
2. `npx nx build api` — webpack build via `NxAppWebpackPlugin` succeeds; `dist/package.json` regenerated without `swagger-ui-express`
3. `npx nx run api:typecheck` — TS 5.9.3 type-checks against the Nest 12 type surface
4. `npx nx test api` — 54 tests (50 baseline + 1 direct rate-limit coverage from task 3.10 + 3 fallback coverage from task 2.2), zero errors/warnings, coverage thresholds intact (80% statements/functions/lines; branches intentionally omitted for api)
5. `npx nx test shared` (8) and `npx nx test web` (221) — zero errors/warnings; no snapshot changes (nothing in web changed — a snapshot diff means an unintended side effect)
6. `npm run lint` — zero warnings
7. `npx nx serve api` — bootstrap without errors; `GET /api/v1/health` → 200 `{ "status": "ok" }`; unknown route → 404 JSON
8. Manual Swagger check (user): `SWAGGER_ENABLED=true` in `apps/api/.env`, restart, `GET http://localhost:3001/api/v1/api/docs` serves the UI
9. `npm audit` — `multer`/`js-yaml` chains gone; before/after counts recorded (~8 fewer expected)
10. E2E (user-run, manual): `npm run e2e` — the 10 API specs in `api-health.spec.ts` exercise the Nest 12 app end-to-end. **Pre-existing flake (ROADMAP I17):** fresh local runs fail intermittently with `ECONNREFUSED :3001` (API readiness races + orphan dev-server processes) — a failure matching that pattern is not a regression of this upgrade; re-run and compare against the documented `develop` baseline before investigating.
11. Direct rate-limit coverage (task 3.10): the new test asserts a 429 with the `ThrottlerException: Too Many Requests` payload from `@nestjs/throttler` 6.5.0 on the Nest 12 app, and the full E2E suite still passes end-to-end (no shared-budget contamination — see "Held-back dependency").
